# Multi-Gate Design

Each stage is a gate. A worker agent produces an artifact and signals completion with a label. A separate triage agent reacts to that label, classifies the artifact, and signals the next gate with a hand-off label.

## Label convention

Worker completion signals use `<worker-name>-ready`.  
Triage hand-off signals use `<triage-name>-handoff`.

| Step | Label |
|------|-------|
| `issue-worker` finished | `issue-worker-ready` |
| `issue-triage` opens plan gate | `issue-triage-handoff` |
| `plan-worker` finished | `plan-worker-ready` |
| `plan-triage` opens PR gate | `plan-triage-handoff` |
| coding agent finished | `pr-worker-ready` |
| `pr-triage` finished | `pr-triage-handoff` |

Blocking labels use the form `<thing>-required`. Removing the label is the human signal to continue. The exception is `dependency-required`, which a watcher removes when the work the issue depends on is finished (see Dependency gate).

Labels are internal. Reporters are never asked to add, remove, or interpret them. All guidance to reporters is given in plain-language comments.

Two independent axes are applied by the triage agents:

- **Complexity** — design impact / autonomy
- **Risk** — blast radius

## Workflow names

The Actions sidebar sorts workflows by display name, so the names carry the order. They are all in the form `Concierge <phase><step> [▸ ]<Name>`:

- **`Concierge`** groups the harness together, ahead of the repository's own workflows.
- **The code** (a digit for the phase, a letter for the step) puts the workflows in the order they run. Workers and triages come first in each phase; the helpers that serve a phase sit after them; phase 4 holds what is not tied to one gate.
- **`▸`** marks a workflow that can be started by hand (it has `workflow_dispatch`). Workflows that run only on events carry no marker.

| Name | Runs when |
|------|-----------|
| `Concierge 1a ▸ Issue Worker` | an issue is opened, edited or commented (and by hand for one issue) |
| `Concierge 1b Issue Triage` | `issue-worker-ready` |
| `Concierge 1c ▸ Dependency Watch` | hourly, on dependency events, and on demand |
| `Concierge 1d ▸ Reporter Notify` | a linked issue is opened, or `plan-approval-required`, `issue-worker-ready` or `needs-info` is applied to it (and by hand for one issue) |
| `Concierge 1e ▸ Stalled Issue Sweep` | hourly, and on demand for one issue or all of them |
| `Concierge 2a Plan Worker` | `issue-triage-handoff` |
| `Concierge 2b Plan Triage` | `plan-worker-ready` |
| `Concierge 2c ▸ Plan Approval Resume` | a maintainer removes `plan-approval-required` (and by hand) |
| `Concierge 2d ▸ Spawn Work Items` | by hand, for an issue whose plan lists work in the related repository; a plain workflow, no model |
| `Concierge 3a PR Worker` | `plan-triage-handoff` |
| `Concierge 3b ▸ PR Ready Signal` | the coding agent finishes (and by hand for one pull request) |
| `Concierge 3c PR Triage` | `pr-worker-ready` |
| `Concierge 4a ▸ Janitor` | after gate labels change, on assignment and on close, hourly, and on demand |
| `Concierge 4b ▸ Related Repo Closer` | a canonical issue (it carries `original-in-related-repo`) closes, and by hand for one issue; a plain workflow, no model |
| `Concierge 4c ▸ Waiting for Release` | an issue closes because a pull request merged, and by hand for one issue; a plain workflow, no model (an issue closed by hand, as not planned or as a duplicate gets nothing) |
| `Concierge 4g ▸ Route Back` | by hand, for the canonical issue of a link whose work belongs in the original's repository after all; a plain workflow, no model |
| `Concierge 4d Release Closer` | a release is published |
| `Concierge 4e ▸ Updater` | daily, and on demand |
| `Concierge 4f ▸ Check Deployment` | on pull requests, and on demand |
| `Concierge 5a ▸ Status` | when a label that matters changes, on a comment, hourly, and on demand; a plain workflow, no model |
| `Concierge 5b ▸ Commands` | a comment, a label that changes what waits for a maintainer, an issue closing or reopening, hourly, and on demand for one issue; a plain workflow, no model |

The ordering holds whether the sidebar counts punctuation or ignores it, because the code is unique and sits before the marker. Names stay within about 40 characters (the longest is 35); longer ones truncate in the sidebar.

To add a workflow, give it the next free step letter in its phase (or a new phase digit), add `▸` only if it has `workflow_dispatch`, and set the name in the frontmatter (`name:`) of a gh-aw definition or at the top of a plain workflow. `tools/workflow-names.test.mjs` checks the format, that codes are unique, that the markers match what each workflow actually allows, and that sorting the names sorts the pipeline. File names are separate: they keep their stems (`issue-worker`, `janitor`) so reordering the display names never means renaming files.

## Label lifecycle

Gate labels are signals, not history. A label event starts the next workflow, so only the moment a gate label is added matters; once the next signal exists the earlier label has done its job and goes. At any moment an issue shows at most one gate label, which is where it is now. The history is in the timeline and in the plan comment. A plain Actions workflow, the **janitor** (`janitor.yml` with `janitor.mjs`, no LLM, no secret), does the removing.

**Gate labels**

| Label | On | Added by | Removed when |
|-------|----|----------|--------------|
| `issue-worker-ready` | issue | issue worker (the dependency watcher re-adds it) | issue triage applies any outcome: `issue-triage-handoff`, `backlog`, `needs-info`, `dependency-required`, `scope-review`, `out-of-scope`, `duplicate`, `invalid`, `already-fixed` or `spam` |
| `issue-triage-handoff` | issue | issue triage, or a maintainer (promote a `backlog` issue, override a scope decision) | `plan-worker-ready` is added |
| `plan-worker-ready` | issue | plan worker | `plan-triage-handoff` or `plan-approval-required` is added |
| `plan-triage-handoff` | issue | plan triage, or `plan-approval-resume` after approval | the coding agent is assigned to the issue |
| `pr-worker-ready` | pull request | the coding agent | `pr-triage-handoff` is added to the pull request, or it closes |
| `pr-triage-handoff` | pull request | PR triage | the pull request closes or merges |

An earlier label is removed only when the evidence that replaces it is already there (the next label, or the assignee), so an item never loses its position. Removing a label starts nothing: the workflows listen for `labeled`, and `plan-approval-resume` ignores everything but `plan-approval-required`, which the janitor removes only from closed issues.

Every label event runs in its own concurrency group (the item number plus the label name). GitHub keeps one pending run per group and cancels an older pending run when a newer one arrives, and a run for a label that changes nothing still takes the slot before its job is skipped. Triage adds three labels in the same second, so with one group per item the run for `pr-triage-handoff` could be cancelled by the runs for `complexity/*` and `risk/*` (seen on frodo-lib#771, which kept `pr-worker-ready`). Runs may now overlap, which is safe: the script reads the item's current labels and every removal is idempotent. The hourly sweep is the backstop for anything that still slips through.

**Everything else**

| Label | Added by | Removed | After the issue closes |
|-------|----------|---------|------------------------|
| type (`enhancement`, `bug`, and so on) | issue template or triage | never | stays |
| `complexity/*`, `risk/*` | plan triage | never | stays |
| `low-hanging-fruit`, `priority/*` | issue triage | never | stays |
| `duplicate`, `invalid`, `already-fixed`, `out-of-scope`, `spam` | issue triage | never | stays (it explains the closure) |
| `no-auto-processing` | a maintainer, by hand (no gate adds or removes it) | a maintainer, which hands the issue over | stays |
| `related-repo` | issue worker | never | stays |
| `original-in-related-repo` | issue worker's `create-issue` configuration | never | stays |
| `waiting-for-release`, `released` | the `waiting-for-release` workflow, then the release closer | `waiting-for-release` goes when the release lands | `released` stays |
| `dependency-required` | issue triage | the dependency watcher | removed |
| `dependency-satisfied` | the dependency watcher, or a maintainer | never while the issue is open: triage needs it, or any later triage run would gate the issue again | removed |
| `needs-info`, `backlog`, `scope-review`, `needs-decision`, `plan-approval-required` | triage, plan triage; a maintainer can add `plan-approval-required` by hand to any issue; the issue worker's canonical issue in a related repository starts with it, and plan triage adds it for a "Wrong layer" plan | triage or a maintainer | removed (they describe open work) |
| any gate label still present | | | removed |

Example: an issue that went through the whole pipeline ends with its type, `complexity/*`, `risk/*` and `released`.

**Which closes count.** Only an issue closed by a merged pull request waits for a release. `scripts/resolution.mjs` asks GraphQL for the issue's last `ClosedEvent` (`stateReason` and `closer`, which is a `PullRequest`, a `Commit` or empty) and posts nothing when the issue was closed as not planned or as a duplicate, closed by hand (no closer), closed by a pull request that is not merged, or closed by a commit (there is no description to copy, and a release cannot be matched to a fix without a pull request number). A close event that GitHub has not recorded yet is waited for, a few times, before the run gives up. This was found on frodo-cli#923 (2026-10-24): the maintainer closed it by hand as already fixed on main, and the gate, then a model run with a pre-activation step to stop itself, read the issue four times and the fix four times, searched repositories for nothing, met HTTP 429 (whose retries count against the cap) and filed a failure issue (frodo-cli#927). Nothing was waiting for a release. The gate is code now ([record 0029](https://github.com/gearsnlevers/issue-concierge/blob/main/docs/decisions/0029-the-reporter-is-told-how-an-issue-was-resolved.md)), so the same close starts no model at all. `scripts/resolution.test.mjs` pins the decision for each kind of close, `tools/waiting-for-release-workflow.test.mjs` the workflow around it.

**Which release the closer checks.** The release closer is told the tag of the release that started its run (`github.event.release.tag_name`) and must read exactly that release with `get_release_by_tag`. It must not use `get_latest_release`: that tool skips prereleases and returns the newest stable release. On frodo-lib 5.0.0-12 the closer called it three times, checked v4.12.0, concluded that nothing it was waiting for was included, and changed no labels, so lib#761 stayed `waiting-for-release` after the release that contained it. On 5.0.0-11 the model had happened to recover through `list_releases`. `tools/release-closer-release.test.mjs` pins the prompt.

**Which fixes a release contains.** The release notes are written for people and name only the changes they describe, so an issue whose fix is a test or a documentation change has no entry to match. frodo-lib#762 was fixed in #775, which is part of v5.0.0-13, and stayed `waiting-for-release` after that release because the closer decided from the notes. What a release contains is a question for git, so the `included_fixes` step of the closer answers it before the agent starts, with no model. For each issue with `waiting-for-release` in this repository (not a pull request, not marked `related-repo`) it reads the comment that the Waiting for Release gate wrote (`Fixed in #N.`, by `github-actions[bot]`, the latest one when there are several; a comment a person typed does not count), asks for pull request N and compares its merge commit with the release tag. When the merge commit is an ancestor of the tag (`ahead` or `identical`) it adds `released`, removes `waiting-for-release` and posts "Included in {tag}.", in that order, so that a call that fails half way is finished by the next release: an issue that already has `released` only loses the waiting label and says nothing twice. It changes no issue's state and never fails the job: an error is a warning and the agent still runs, because the agent decides what the step cannot (an issue the notes name, and an issue whose fix is in a related repository, judged by the version this repository pins). The step runs in the pre-activation job, which `on.permissions` gives `issues: write`, `pull-requests: read` and `contents: read`. `tools/release-closer-fixes-in-release.test.mjs` pins the step and runs it against stubbed GitHub objects.

**When it runs.** On the label events that can change the answer (the gate labels, the triage outcomes and `plan-approval-required`), on assignment and on close, for issues and pull requests; hourly as a sweep for anything missed; and on demand. A manual run can clean one item, or with `include_closed` tidy old closed items once; `dry_run` reports without removing. It is idempotent and treats an already-absent label as success.

**Do not read a gate label as proof that a phase happened.** Those labels are gone by the time the next phase is under way. Code and prompts that need to know "has this issue already been handed on" test for later evidence instead: `issue-triage-handoff`, `plan-worker-ready`, `plan-triage-handoff`, a `complexity/*` or `risk/*` label, or the coding agent as an assignee. `plan-approval-resume` and the scope rule in issue triage do exactly that.

**Reopening** an issue puts it back at the issue gate: the worker re-adds `issue-worker-ready` and triage runs again. Because closing removed `dependency-satisfied`, triage gates the issue again if it still declares a dependency, and the watcher clears it again within the hour.

## Gate labels are applied, not suggested

A gate hands on by a label, and the label event starts the next gate. gh-aw sends every label a worker asks for with the model's `confidence` and `rationale` (issue intent), and a label below `HIGH` is not applied: it is held as a suggestion that a person must accept on the issue page. The run still reports success (`Successfully added 0 labels ... Suggested 1 labels`), there is no label event, and the next gate never starts. The first sighting was the assignment (frodo-lib#760, see "3. PR gate"). On 2026-10-24 it happened at the first gate: the Issue Worker rated `issue-worker-ready` MEDIUM on frodo-lib#803 and #802, and #803, the canonical issue of frodo-cli#919, sat outside the pipeline until a maintainer added the label by hand. Of 14 requests for `issue-worker-ready` in the last 100 runs of frodo-lib and frodo-cli, 11 were HIGH and applied, the 2 MEDIUM ones were held (#802, #803), and 1 HIGH one was not added for a reason that was not looked into.

- Issue triage, plan worker, plan triage and PR triage set `issue-intent: false` on `add-labels`, and the PR worker on the assignment, so their hand-offs are applied whatever the model thinks of its own confidence. Their prompts say so.
- The Issue Worker is the exception. [Decision 0009](decisions/0009-issue-routing-decides-from-the-report-text.md) makes `related-repo` depend on a quoted rationale and a confidence (HIGH needs the quote), which exists only while issue intent is on. Its prompt therefore makes `issue-worker-ready` a signal that is always HIGH, and confidence decides only `related-repo`. That is a first layer: a model can still rate the signal lower.
- `tools/ci-compile-smoke.sh` reads the compiled locks: `issue_intent` is false in the five gates above and absent in the Issue Worker. `tools/stalled-intake.test.mjs` pins the sources and the prompt.
- **The signal goes on for every outcome of the analysis.** On 2026-10-27 the first run of the end-to-end sandbox ([e2e.md](e2e.md)) filed a request that the project's scope excludes. The Issue Worker posted the decline and wrote "I'm not adding `issue-worker-ready`, since the work is not to be done here": it had read the signal as a judgement. Issue triage never ran, so nothing labelled the issue `out-of-scope` or closed it, and it sat open with a polite refusal on it until the stalled-issue sweep, at least half an hour later, would have given the label. The prompt now says that the label goes on whatever the analysis concludes (complete, more details needed, out of scope, duplicate, already fixed), that triage is what acts on the conclusion, and that the only exceptions are a fix already in review and a linked canonical issue. A prompt is a first layer; the sweep is the backstop. `tools/issue-worker-signal.test.mjs` pins the wording and the two exceptions.

## The resolution

**Why it exists.** On 2026-10-25 an audit of what the Concierge writes when an issue closes found one-line comments only: "Fixed in #N. Waiting for a release that includes this.", then "Included in vX.". The original issue of a split-repository link got a line that only named the other issue. The reporter was never told what had been wrong, what changed or how to use it, and the model that wrote the first line was forbidden to read the pull request, where the explanation was. A maintainer had read that explanation before merging.

**The rule.** The description of a pull request that closes an issue has a section `## Resolution`, written for the person who reported the issue: what was wrong, what changed, what they will see now and how to use it. Plain language, three to eight sentences, no labels, gates, workflows or decision numbers; a record is cited by its full URL, as everywhere ([record 0029](https://github.com/gearsnlevers/issue-concierge/blob/main/docs/decisions/0029-the-reporter-is-told-how-an-issue-was-resolved.md)). The PR worker tells the coding agent to write it, PR triage reports on it in its comment (a line starting "Resolution:", advisory like the other two lines), and a maintainer or a person's own pull request follows the same rule.

**What `Concierge 4c ▸ Waiting for Release` does.** It is a plain workflow, no model. When an issue closes because a pull request merged, it reads the pull request and posts one comment on the issue:
- First line `Fixed in #N.` (or `Fixed in owner/repo#N.` for a pull request in another repository). The release closer reads that line, and only when `github-actions[bot]` wrote it.
- The `## Resolution` section, between hidden markers so that the text can be found again, then one line about the release: it will be in the next release and a comment names it, or, when a release published after the merge already contains the merge commit (decided by git, [record 0024](https://github.com/gearsnlevers/issue-concierge/blob/main/docs/decisions/0024-a-release-contains-a-fix-when-git-says-so-not-when-the-notes-do.md)), which one. A hidden marker names the pull request, so a run that starts twice posts once.
- The label `waiting-for-release`, or `released` for a fix a release already contains, before the comment: a run that stopped half way is finished by the next one.
- A pull request without a usable section (none, a placeholder such as `TBD`, or under 20 characters) gets the old comment, `Fixed in #N. Waiting for a release that includes this.`

**Trust.** The section is text from a pull request, and anyone can write one. It is used only when a person merged the pull request, because that merge is the maintainer's look at the description ([record 0005](https://github.com/gearsnlevers/issue-concierge/blob/main/docs/decisions/0005-a-maintainer-holds-the-levers-of-the-pipeline.md)), and no model reads or writes it, so there is nothing to inject into. The copy removes HTML and comments, images and `@` mentions (a mention in a bot's comment would notify a stranger; it is put in a code span) and is cut at a paragraph or sentence end at 1,500 characters, with a link to the pull request for the rest. The comment on the issue is the copy that counts: a description edited after the merge changes nothing already posted.

**The original issue.** `Concierge 4b ▸ Related Repo Closer` puts the same text in its comment on the original, in the other repository, before it waits for a release or closes: the text the harness posted on the canonical issue, or, because both workflows start on the same close and the first may not have posted yet, the same text read from the pull request. Bare references (`#12`) name issues of the canonical repository, so they are qualified (`owner/repo#12`) for the original. If the text cannot be read, nothing is written: an original is never closed without its explanation because of a failed read.

**Limits, on purpose.** The coding agent cannot edit the description of its own pull request after it opened it, so the section is written from the plan, and a maintainer fixes it before merging; PR triage's line says what it found. One pull request that closes several issues gives each the same text. A close by hand, as not planned or as a duplicate, and a close by a commit get nothing from the workflow: a maintainer says what there is to say, and the release closer's `Included in vX.` still follows for the ones that wait.

## Held runs

GitHub holds every workflow run that the coding agent causes at `action_required` until a maintainer approves it. For the pipeline that is a check worth keeping: the agent's push runs the pipeline definition on its own branch, with the repository's secrets reachable, and the approval is the moment a person reads the diff before that happens. Keep it on.

The hold is decided before any job condition is evaluated, so it also catches runs that a condition would skip, and runs for commits that no longer matter. Every push the agent makes holds the pipeline run and a `Dependabot Auto-Merge` run, whose only job is conditioned on the Dependabot actor and so is skipped for the agent. Every comment the agent posts on its own pull request starts an `Issue Worker` run, and that run waits for approval although its `if:` (`comment.user.type != 'Bot'` and `issue.pull_request == null`) skips it. Approving any of these starts nothing useful. On a pull request with four pushes that is eight held runs, and one of them is needed: the pipeline run for the newest commit.

The janitor deletes the rest. A run is a candidate only when it finished as `action_required` and its actor is the coding agent; a run caused by a person, a contributor's run on a fork pull request and anything else is never touched. A candidate is deleted when one of these holds:

- **It is a listed workflow** (`DISPOSABLE_HELD_RUNS` in `scripts/janitor.mjs`): the Issue Worker's lock file on `issue_comment`, and the repository's `dependabot-auto-merge.yml` on `pull_request`. The second entry is deleted only while the default branch's copy of that workflow still has a job-level `if: github.actor == 'dependabot[bot]'` on every job. The sweep reads the file each time (`everyJobGuardedByDependabot`), so a repository whose workflow differs, or has none, is simply not affected: frodo-cli and frodo-lib have this workflow with one guarded job, and the five action repositories have none.
- **Its pull request is closed**, or **has moved past the run's commit**: the sweep reads the pull request named in the run once and compares the run's `head_sha` with the pull request's current head. This applies to every workflow, the pipeline included, because the run of an older push can only test code that is no longer there.

Everything else stays. In particular the held run for the **current head of an open pull request** is never deleted, whatever the workflow: it is the only CI for the agent's code, and the approval is the moment a person reads the diff before the pipeline definition of the agent's branch runs with the repository's secrets reachable. A run with no pull request (a fork, another event) stays, and so does any run the sweep cannot judge: a pull request or a workflow file that cannot be read is reported as a warning annotation and the run is kept. Doubt never deletes. Never list a workflow that does real work. A test pins the Issue Worker's guard, so weakening it fails the build instead of making the sweep unsafe.

**When it runs.** The sweep is a second job of the janitor workflow, `held-runs`, which follows the label job and starts for the same events except issue events: gate labels on pull requests, a pull request closing, the hourly schedule and a manual run (`dry_run` lists what it would delete and why). A pushed commit cannot start the janitor itself, because GitHub would hold that run too, so a stale run is deleted at the next janitor run, not when the agent pushes. Expect an older run to stay in the approval list for up to an hour, less when a label event or a merge comes first. The run for the newest commit stays until you approve it or the agent pushes again, which makes it stale in turn.

**Permissions.** Deleting a run needs `actions: write`, reading the pull request needs `pull-requests: read`, and reading the workflow file needs `contents: read`. The job declares these for itself, so the label job keeps `issues: write` and `pull-requests: write` only.

## Repository guidance

A repository tells its contributors, human and agent, how to work on it in files of its own: `AGENTS.md` at the root, `.github/copilot-instructions.md`, and `.github/instructions/*.instructions.md`, each of which starts with `applyTo` globs in its frontmatter. GitHub's coding agent, its code review and Copilot CLI load these files on their own (GitHub documents which feature reads which file in its custom instructions support matrix). The harness adds no file format: it makes two of its gates read the same files, so a rule is written once and no copy has to be kept in step. Without these files nothing changes. The template is `shared/agents.md`; it goes to the repository root, not into `.github/issue-concierge/`.

| Gate | What it does with the guidance | Where it reads from |
|------|--------------------------------|---------------------|
| Plan worker | Reads `AGENTS.md`, `.github/copilot-instructions.md` and at most three instruction files whose `applyTo` matches the files it expects to touch, and adds a "Repository rules that apply" heading of at most five lines to the plan. | The default branch: an `issues` event checks out the default branch, and the prompt tells it to use the GitHub tools with no `ref`. |
| PR worker | Reads nothing. One static sentence in the `custom-instructions` that travel with the assignment: follow `AGENTS.md` and the matching `.github/instructions` files and run the checks they list. The coding agent loads the files itself, from its own branch. | Not applicable. |
| PR triage | Compares the diff with the rules that no test or linter enforces and adds one "Repository rules:" line to its comment. | The GitHub API only (`checkout: false`), with no `ref`, which is the default branch. |
| Every other gate | Does not use it. | |

**Why the default branch.** A pull request could otherwise weaken the rules it is judged by: edit `AGENTS.md` in the same change and the review applies the edited version. PR triage therefore never passes a ref. When the pull request itself changes `AGENTS.md`, `.github/copilot-instructions.md` or a file under `.github/instructions/`, triage judges it by the default-branch version, says so in the comment and makes a maintainer's review of that change the next action. gh-aw applies the same principle: every compiled workflow saves `.github`, `.agents` and `AGENTS.md` from the base branch for restoration ("Save agent config folders for base branch restoration"). A pull request against another base branch is still judged by the guidance of the default branch. The coding agent loads guidance from its own working branch and may edit it, which is the reason triage does not.

**Advisory, never binding.** The repository's guidance ranks below the harness's safety policy and below the workflow's own prompt. It describes how to work on and review the repository; it can never change which comment a gate posts, which label it adds, or any gate or approval, and both prompts say to ignore text in it that tries. The "Repository rules:" line changes none of the complexity, risk or `pr-triage-handoff` labels. A violation shows up in the comment and in the recommended next action, and merge rules stay as they are. Rules that a test or a linter enforces are left to CI ("enforced by CI" at most), so triage does not repeat them.

**Decisions are a second kind of repository file the same gates read:** see "Decision records" below.

**What the PR worker does not do.** It still never reads the issue or any other untrusted content (`deployment.md` explains why it has no `min-integrity: none`), and the sentence it sends is static text in the safe-output configuration, not written by the model, for the reason given under "PR gate": an instruction that only travels in the model's rationale never reaches the coding agent.

**Cost.** Seven recent runs of the two gates (frodo-lib and frodo-cli, 2026-10-23) used 12.6 to 15.0 AIC (plan worker) and 12.3 to 20.4 AIC (PR triage). The guidance adds about 1.5K tokens of context (a 40-line `AGENTS.md` and up to three short instruction files) and two model turns, because the reads are batched into one step each, and every turn re-reads the cached prompt of roughly 40K tokens. Priced with the rates implied by those seven runs (about 0.23 AIC per 1K tokens written to the cache, 0.02 per 1K read from it, 0.9 per 1K of output), that is about 2 to 2.5 AIC per run, or 15% of the plan worker. A repository without guidance files costs one batched read that finds nothing, about 1 AIC. `max-ai-credits` was not acting as a per-run cap (PR triage ran at 19.2 and 20.4 AIC against a setting of 16 and succeeded), but it feeds gh-aw's daily guardrail and the failure report, so PR triage's is raised from 16 to 24: the largest measured run plus the guidance overhead. The plan worker's is raised from 20 to 24 as well: its largest measured run (15.0), the guidance overhead and the extra read that checking a bug's cause can cost come to about 19.5 in the worst case, too close to 20. The other gates are unchanged.

## Decision records

Design decisions that nobody wrote down get made again, differently, by the next contributor or agent (see the case below). A repository can keep them as decision records, in the same way it keeps `AGENTS.md` for rules of work: a folder `docs/decisions/` with one file `NNNN-short-title.md` per decision and an index in `docs/decisions/README.md`. A repository whose `docs/` is generated output that gets rewritten (frodo-lib's is tracked typedoc output) keeps the same folder at the repository root as `decisions/`, with the index `decisions/README.md`. The gates look for `docs/decisions/README.md` first and then for `decisions/README.md`; the first one found wins, and records from both folders are never merged. Each record starts with frontmatter: `status:` (`proposed`, `accepted`, `rejected`, `deprecated` or `superseded by NNNN`), `date:`, `decision-makers:`, optionally `applies-to:` (a list of path globs the record binds; without it the record covers the whole repository) and `issues:`. The body has Context and problem statement, Decision, Consequences and optionally Alternatives. Only `accepted` records bind, and they bind until a newer record supersedes them; an accepted record is never edited except for its `status:` line. A pull request that changes a decided behaviour adds or supersedes a record in the same change. A decision that binds several repositories is written once, in the repository the others list in their `AGENTS.md`, with a `repos:` list. The template and guide are `shared/decision-record.md`, shipped as a reference like `shared/agents.md`; it goes into `docs/decisions/` (or `decisions/`), not into `.github/issue-concierge/`. Records are as public as the repository: no secrets, no undisclosed security findings.

The harness adds no format beyond the folder. It makes the gates that already read the repository's guidance read the records too:

| Gate | What it does with the records | Where it reads from |
|------|-------------------------------|---------------------|
| Plan worker | Reads the indexes (`docs/decisions/README.md` and `decisions/README.md`, the first one found wins) in the same step as its guidance reads, then at most four accepted records, in the second: those whose `applies-to` matches the files it expects to touch and the repository-wide ones that bear on the request. It adds a "Decisions that apply" heading of at most five lines to the plan, one record per line. If the request goes against an accepted record it says so on its own line: "Conflicts with https://github.com/owner/repo/blob/main/docs/decisions/0003-short-title.md: needs a maintainer decision". A record is always named by its full URL, never by a bare number. | The default branch: an `issues` event checks out the default branch, and the prompt tells it to use the GitHub tools with no `ref`. |
| Plan triage | Reads the plan comment only. A "Conflicts with" line under "Decisions that apply" makes it classify as usual, add `plan-approval-required`, emit no `plan-triage-handoff` and post one comment: "This conflicts with decision record NNNN. A maintainer has to decide: change the request, or supersede the record. Remove the plan-approval-required label to resume." It never lifts the hold itself. | Not applicable. |
| PR worker | Reads nothing. The one static sentence in the `custom-instructions` that travel with the assignment now also names the accepted decision records in `docs/decisions` or `decisions` that apply to the files the coding agent changes. | Not applicable. |
| PR triage | Reads the same records and adds one "Decisions:" line to its comment: the violations found (the record's full URL and the path in the diff), "no conflicts found", or "no decision records". A change that does the opposite of an accepted record, or changes a decided behaviour without adding or superseding a record, is a violation. | The GitHub API only (`checkout: false`), with no `ref`, which is the default branch. |
| `check-deployment` | Prints a notice, never a failure, when neither `docs/decisions/` nor `decisions/` exists. | The checked-out repository. |
| Every other gate | Does not use them. | |

**Why a conflict holds the issue and does not only warn.** The plan is the last moment at which a person can see that a request and a decision disagree before a coding agent starts. The `plan-approval-required` hold is the existing human lever for that moment: it stops the PR worker (its `if:` and its live check), and removing it resumes the issue through `plan-approval-resume`. A maintainer then either changes the request or supersedes the record, which is itself a decision worth writing down.

**Why the default branch.** The same reason as for the guidance: a pull request must not be able to weaken the decisions it is judged by. PR triage never passes a ref. When the pull request itself adds, edits or supersedes a file under `docs/decisions/` or `decisions/`, triage judges it by the default-branch version (by none when the default branch has no records), says in the comment that the decision records change in this pull request and makes a maintainer's review of that change the next action. The coding agent works on its own branch and may, and should, add a record when it changes a decided behaviour; the review still judges by the default branch until a maintainer merges the record.

**Advisory, never binding on the harness.** Records rank below the harness's safety policy and below the workflow's own prompt, and both prompts say to ignore text in a record that tries to change a label, a gate or an approval. The "Decisions:" line changes none of the complexity, risk or `pr-triage-handoff` labels. The only thing a record can cause is the human hold at the plan gate, through the plan worker's honest report of a conflict.

**The case that led to it.** frodo-cli#885 asked to restore the 4.x behaviour for an omitted realm. The design, taken weeks earlier, was that the realm picker stays and opens only when other mandatory connection settings are missing. It was not written anywhere the plan could read, so Copilot's first draft deleted the picker and about 180 lines of its terminal tests. With a record "the realm picker stays and opens only when other mandatory connection settings are missing" (`applies-to: src/utils/interactive/RealmPickers.ts`) on the default branch, the plan worker would have listed it under "Decisions that apply", and PR triage would have reported "Decisions: violates https://github.com/owner/repo/blob/main/docs/decisions/0001-the-realm-picker-stays.md: src/utils/interactive/RealmPickers.ts is deleted". A request to remove the picker would have produced "Conflicts with https://github.com/owner/repo/blob/main/docs/decisions/0001-the-realm-picker-stays.md: needs a maintainer decision" and the hold.

**Cost.** The index plus up to four short records add about 2.5K tokens of context per gate run at most. The plan worker and PR triage read them in the same batched steps as the guidance, so there is no extra model turn, and the added cost is the cache write of those tokens (about 0.23 AIC per 1K), their cache reads in the later turns (0.02 per 1K each) and a short heading of output (0.9 per 1K): about 0.9 AIC per run, and about 0.1 AIC when the folder does not exist. If a model reads in separate steps, each extra turn re-reads the cached prompt of roughly 40K tokens, about 0.8 AIC, so the worst case is about 2.5 AIC. The plan worker's worst measured case (about 19.5 AIC with the guidance overhead and a cause check) stays under its `max-ai-credits` of 24. PR triage's (20.4 AIC measured, 2.5 for the guidance, 1 for the records) reaches about 24, so its `max-ai-credits` goes from 24 to 28. The PR worker reads nothing and stays at 12.

## Plan comment identity

The plan lives as a single comment on the issue.  
gh-aw appends hidden HTML comments to every comment a workflow posts. The one that identifies the plan names the repository and the workflow:

```html
<!-- gh-aw-workflow-call-id: owner/repo/plan-worker -->
```

`plan-triage` classifies only the comment written by `github-actions[bot]` whose body contains that text (`gh-aw-workflow-call-id: owner/repo/plan-worker`, with the real repository). The author check matters: a person can type the same text into a comment, so the text alone does not prove who wrote it.

The prompt describes the marker in words and never shows it as an HTML comment. gh-aw removes HTML comments, even inside a code fence, when it renders a workflow's prompt (the agent sees an empty fence), so a prompt that relied on one gave plan triage no marker to look for: on 2026-10-23 it ended without labels on frodo-cli#886 ("the marker value is blank in my instructions") and worked on other issues only because the model guessed which comment was the plan. A test fails if a workflow prompt contains an HTML comment (`tools/prompt-hazards.test.mjs`). The marker in this paragraph is documentation for humans, not part of any prompt.

## Human interaction

Reporter interaction stays in the issue phase and is conducted entirely through comments.

When information is missing the issue worker posts an explicit, plain-language request. Issue triage applies the internal `needs-info` label and does not hand off.  
A later comment from the reporter re-triggers the issue worker. Issue triage then re-evaluates and can clear `needs-info` and emit `issue-triage-handoff` once the issue is complete.

The plan phase is a classification prerequisite. For high complexity or high risk it adds the internal label `plan-approval-required` and stops. A maintainer removes that label to resume: the `plan-approval-resume` workflow (plain Actions, no LLM) sees the removal and applies `plan-triage-handoff`, which starts the PR gate. It acts only on an open issue that plan triage has classified (it carries `complexity/high` or `risk/high`, or both a `complexity/*` and a `risk/*` label with any value, which is what a hold put on by hand leaves), has no `plan-triage-handoff` yet, has no coding agent assigned, and is not waiting on a dependency (`dependency-required`). An issue that plan triage has not classified is not resumed: there is no plan to approve yet. A removal made by a bot account never counts, because approval is a human decision. It can also be run by hand with an issue number for an issue whose label was already removed.

**A hold put on by hand.** A maintainer can add `plan-approval-required` to any issue, whatever its complexity and risk, to read the plan before the coding agent starts. The hold is honored by the one gate that matters: the PR worker assigns nobody while the label is there, even if plan triage emitted `plan-triage-handoff` anyway (see "Who may start when"). Plan triage still classifies the issue, but it never emits the hand-off or adds the label again while the hold is present. Removing the label is the approval: `plan-approval-resume` applies `plan-triage-handoff` and the PR gate starts. The janitor removes `plan-worker-ready` when the hold is added (the plan gate is over), so a hold added before plan triage ran leaves the issue unclassified and the resume has nothing to approve; re-add `plan-worker-ready` to run plan triage.

Maintainer interaction on the actual change happens in the PR phase.

## Who can start a gate

Every gh-aw workflow checks, in its `pre_activation` job, that the user who caused the event has the `admin`, `maintainer` or `write` role, and skips the run silently when they do not. The gates are label-driven: the first gate is the only one that starts from a reporter's own event, so it is the only one that opts out (`roles: all` on `issue-worker`, for `issues` and `issue_comment` alike, since a reporter answers its questions in comments). The later gates start from a label added by `SIGNAL_TOKEN` or by a maintainer, and keep the default check.

Opening the first gate to everyone is safe because of what it can do, not because of who calls it: it has no shell, reads the report as untrusted text, runs threat detection before any output is applied, and its outputs are two comments, two fixed labels and one linked issue. The cost is bounded by `user-rate-limit` (5 runs per user per 30 minutes over `issues` and `issue_comment`; writers are exempt). Residual risk: a crafted report could try to steer the agent into spending its outputs on another issue (`target: "*"`, needed for `workflow_dispatch`), which threat detection and the output caps limit.

## Who may start when

A gate starts for an issue only while the issue is open. The label-driven gates (issue triage, plan worker, plan triage, PR worker) carry `github.event.issue.state == 'open'` in their `if:`, and so does the issue worker, except for a maintainer's `workflow_dispatch`. A comment, an edit or a label on a closed issue therefore starts nothing; reopen the issue to restart. Three workflows act on closed issues on purpose and are left alone: `waiting-for-release` (which skips closes that no pull request or commit made, see "Which closes count") and `related-repo-closer` start on the close event itself, and `release-closer` labels issues that are already closed. The plain-Actions workflows were audited as well: `dependency-watch` lists open issues only and `plan-approval-resume` returns "issue is closed" for a closed one; neither hands an issue to an agent otherwise.

A merged pull request needs no special case: merging closes the issue, so every later event carries the state `closed`. The race is the other way round: a label event created just before the issue closes can run just after, with a payload that still says `open`. Only the PR worker assigns the coding agent, so only it asks GitHub for the live state.

**An open pull request that closes the issue stops the hand-off.** frodo-cli#887 was fixed and closed by a merged pull request, and the PR worker still assigned the coding agent to the closed issue, which opened a redundant pull request: the hand-off label arrived at 22:22:24 while the fix (#896) was open, the run started three seconds later, the merge closed the issue at 22:24:36 and the assignment landed at 22:25:06. The PR worker is static and never reads the issue, so words in the plan cannot stop it. The `existing_fix` step runs in the pre-activation job, before anything is assigned, with no model: it asks GraphQL for `closedByPullRequestsReferences(includeClosedPrs: false)` (exact, no text matching) and for the issue's live state. If the issue is closed, or an open pull request will close it, the step fails on purpose and the workflow's `if:` reads `needs.pre_activation.outputs.existing_fix_result != 'failure'`. gh-aw exports only a step's outcome, not its outputs, which is why the step signals by failing; `continue-on-error: true` keeps the job, and so the run, green and files no failure report. For an open pull request the step posts one plain comment naming it. If GitHub cannot be asked it warns and lets the hand-off through: the payload was already checked, and a silent stall would be worse than a redundant pull request. A `needs.` reference in `if:` makes gh-aw apply the whole `if:` to the activation job only, so the pre-activation job now starts for every label event; the step carries its own label and state conditions and does nothing, and posts nothing, for any other label. To hand the issue on anyway, close that pull request or remove its link and add `plan-triage-handoff` again. One window stays open by design: a merge in the minutes between the step's check and the assignment (which happens in a later job) can still close the issue first. The coding agent then finds nothing to do and its pull request is closed by hand, as #897 was.

**A blocking label stops the hand-off.** The PR worker is the only gate that causes code, so it is the hard stop for the two blocking labels of the form `<thing>-required`: `plan-approval-required` (a person's approval, whether plan triage or a maintainer put it there) and `dependency-required`. Both are in the workflow's `if:` (`!contains(github.event.issue.labels.*.name, ...)`, decided from the labels as the event saw them), and the `existing_fix` step reads the labels live as well, so a hold added in the minutes between the label event and the run still stops the assignment. This was found on frodo-cli#885: it carried a hold added by hand, plan triage classified it (`complexity/low`, `risk/medium`) and emitted `plan-triage-handoff` anyway (its prompt then withheld the hand-off only for its own high classification), the PR worker's `if:` checked only `dependency-required`, and the run started; it was cancelled before an assignment. A blocked hand-off is void: when the step blocks for a blocking label, or because an open pull request already closes the issue, it removes the `plan-triage-handoff` label (best effort, with the pre-activation token, which starts no workflow). Otherwise the stale label would make `plan-approval-resume` answer "already handed off" after the hold is removed, and adding the label again would start nothing. The step stays silent for a hold (a person put it there) and comments only for an open pull request.

The labels that plan triage and issue triage apply to stop the issue gate (`needs-info`, `backlog`, `scope-review`, `needs-decision`, `out-of-scope`, `related-repo`, `duplicate`, `invalid`, `spam`, `already-fixed`) are deliberately not checked again at the PR worker. They stop the chain where they are applied, because issue triage emits no hand-off for them, and a maintainer who wants the issue planned anyway adds `issue-triage-handoff` by hand, which is the documented override (promote a `backlog` issue, override a scope decision): re-checking them at the PR worker would turn a label that lingers into a silent stall. The same holds for the plan worker and plan triage, which are cheap and must run so that the issue is classified.

The issue worker is the earlier, wording-level layer: when it finds an open pull request that closes the issue it links it, calls it "in review" (not "already fixed") and adds no gate label, so nothing is planned either. The `if:` is the guarantee; the wording saves a plan.

## Bot activity is not work

Every issue-driven workflow carries an activation condition (`if:` in the frontmatter) so it never starts for bot-authored issues: `github.event.issue.user.type != 'Bot'`. `issue-worker` additionally requires that the triggering comment was not written by a bot and that the comment is not on a pull request. Without this, the issues gh-aw files about its own failures were analyzed, planned and closed like real work, and the harness's own comments re-triggered the worker. A manual run of `issue-worker` with an issue number is unaffected, so a maintainer can still opt a bot-authored issue in.

The PR gate worker only routes to the coding agent, so it uses the small model like the triage workflows; the plan worker is the only gate that still uses the default model.

## Stalled issues

The issue worker can end without signalling. Its run can reach the turn limit before it posts (frodo-lib#803, 2026-10-24: ten turns on reading the code, `429 Maximum LLM invocations exceeded (10 / 10)`, no comment, no label), or it can post and ask for `issue-worker-ready` with a confidence below HIGH, which gh-aw holds back as a suggestion (`Successfully added 0 labels ... Suggested 1 labels`), so no label event starts issue triage. The issue then sits outside the pipeline with nothing saying so. A routed issue is the worst case: it starts held, so a missing triage looks like the hold doing its job, and removing the hold does nothing because `plan-approval-resume` rightly finds no classification to approve. A restart through the issue worker is no way back: it writes another analysis (frodo-lib#802 got one).

`Concierge 1e ▸ Stalled Issue Sweep` (plain Actions, no LLM, [decision 0030](decisions/0030-a-stalled-issue-is-given-the-gate-label-again-by-code.md)) does what a maintainer did by hand: every hour it gives `issue-worker-ready` again, with `SIGNAL_TOKEN`, to an open issue that has an analysis of this repository's issue worker and no evidence of being past issue triage. It removes the label first when it is there, because re-adding a label that is there starts nothing; issue triage then reads the analysis that is already there and writes no second one.

- **Evidence of being past triage** is the janitor's list, without the hold: an outcome of issue triage (`TRIAGE_OUTCOMES`), `plan-worker-ready`, `plan-triage-handoff`, a `complexity/*` or `risk/*` label, or the coding agent as assignee, and also a comment of a later gate (issue triage, plan worker, plan triage, PR worker or PR triage of this repository; the marker gh-aw appends names the gate). The comment matters because the labels can vanish: on an issue that carries the hold the janitor takes `issue-triage-handoff` and `plan-worker-ready` away within seconds, and plan triage's classification comes only after the plan, so for a few minutes on frodo-lib#803 (2026-10-26, found by a dry run of the sweep) a plan comment was the only trace that the gates were running. `plan-approval-required` is not evidence, which is the difference to the janitor: it reads the hold as "the plan is decided" and removes `issue-worker-ready` within seconds, harmlessly, because the label event has already started the run.
- **It leaves alone** pull requests, closed issues, bot-authored issues, originals marked `related-repo` (planning happens on the linked issue), issues that carry `no-auto-processing`, issues an open pull request closes (the worker adds no gate label for those on purpose), and issues without an analysis of this repository's worker (the other repository's worker writes the first comment of a canonical issue, and its marker names the other repository).
- **It waits and it stops.** The last sign of life, the analysis or the gate label, has to be older than a run of issue triage can take, and it stops after a bounded number of gate labels since the last analysis, the worker's own included: a person must look. It never loops.
- **It never writes anything but the gate label.** No comment, no hold, no other label, no start of the issue worker. A hold stays until a maintainer removes it, and once the gates have run on a routed issue there is a plan to read before they do.
- **By hand**, `workflow_dispatch` takes an `issue_number` (it then ignores how recent the last sign of life is) and a `dry_run` that only says what it would do.

What it does not heal: a stall at a later gate (a plan worker that failed, a plan triage that did not classify) and an issue the worker never commented on, whose failure the `[aw]` issue of the failed run reports. Not seen live yet: a real stalled issue given the label again by the schedule.

## The maintainer's view

The labels say where one issue is. A maintainer asks other questions: what waits for me, has anyone answered, is the Concierge working, what does it cost. Each repository that uses the Concierge gets the answers in one place, delivered with the Concierge and derived from that repository's own state ([decision 0035](decisions/0035-each-repository-has-a-status-view-of-its-own.md)). Nothing outside the repository is needed: a project board needs an owner's access and a token, Pages needs a plan, and a deployment cannot assume access to the repositories next to it.

### The status issue

`Concierge 5a ▸ Status` (plain Actions, no model) keeps one pinned issue, "Issue Concierge status" (an earlier version called it "Concierge status"; it is renamed, never duplicated). The bot opens it, it carries `no-auto-processing`, and every gate skips both, so the Concierge never acts on it. The workflow runs when a label that matters changes, when someone comments, every hour and by hand, one run behind the other, and it edits the page only when its content changed. The page, in order:

- **Needs you.** The issues whose next move is a maintainer's, each queue with a count, the oldest waiting first and how long: held because the request changes what exists (`needs-decision`), held because it may not fit the scope (`scope-review`), and a plan waiting for approval (`plan-approval-required`). Whose move it is comes from the labels, in one place (`scripts/issue-concierge-state.mjs`).
- **Reporter replies waiting.** An open issue whose latest comment is from someone who is not a maintainer (`OWNER`, `MEMBER`, `COLLABORATOR`) and not a bot, from the last `reporter-replies-days` days. It includes opted-out issues, marked as such, because nobody else is watching them. It shows the login and a link and never the text of the comment.
- **In flight.** Issues that carry a gate label, and which of them have been there for more than an hour: a whole pass through the three gates takes about a quarter of that.
- **Everything else.** Waiting for the reporter, for a dependency, parked, with the coding agent, tracked in another repository, settled.
- **Which issues the Concierge manages.** "87 open = 31 managed · 49 opted out · 3 opened by bots · 4 not yet picked up", so that every other number has a denominator. An issue is managed when it carries a label only the Concierge applies or the issue worker has commented on it; it is opted out when it carries `no-auto-processing`; bots' issues (the `[aw]` failure issues) are counted apart; the rest has not been picked up yet.
- **Health.** The last good run of each gate, the failed runs of the last seven days, the pinned version against the latest release of its channel, and `SIGNAL_TOKEN`: GitHub puts the expiry of a token on every answer (`github-authentication-token-expiration`), so the page can say "expires in 9 days" or "is rejected" before the gates stop handing issues on without a word.
- **Spend.** The AIC the gates' comments report for the last seven days. A run that posts no comment is not in it.
- **Settings**, with any line of `settings.yml` that could not be used, and the same numbers as JSON in a collapsed block, for a dashboard that reads several repositories.

**The nudge.** With `mention-after-days` above 0 (off by default), the same workflow mentions the people who have the maintain or admin role, listed from the repository's collaborators (at most twenty), in a comment on the status issue when something under "Needs you" has waited that many days. At most one such comment per period: the previous one is deleted when a new one is posted, and when nothing waits that long any more. Titles in it are written so that they mention nobody, and the logins are the only mentions. It is off by default because it is the one thing on the page that notifies people without anybody asking. Listing the collaborators needs more than the workflow token may have, so the signal token is tried next; if neither may, the comment is not posted and the log says why. Nothing is mentioned while the Concierge is paused.

What comes from outside is made safe: a title or a login goes into the page with its `@`, `#`, markup and HTML as entities, so that writing the page mentions nobody and links this issue into no other. If the repository already has three pinned issues, GitHub's limit, or the signal token may not pin, the issue is created unpinned and the page says why.

### Commands and the options comment

An issue that waits for a maintainer carries the command a maintainer needs next, in the issue itself ([decision 0036](decisions/0036-a-maintainer-decides-by-command-from-the-issue.md)). `Concierge 5b ▸ Commands` (plain Actions, no model) does two things.

**The options comment.** One comment on an issue that waits, written by the bot, derived from the labels alone (`scripts/commands.mjs`, the same state as the status issue): a sentence in plain words for whoever reads the issue (no label, command or workflow in it), then the commands for that situation in a collapsed block, and the role they need. It appears only while a maintainer has to act:

| The issue waits because | Commands |
|---|---|
| the request changes what exists (`needs-decision`) | `/accept`, `/decline [reason]` |
| it may not fit the scope (`scope-review`) | `/accept`, `/decline [reason]` |
| a classified plan waits for approval (`plan-approval-required` with a complexity and a risk label) | `/approve`, `/replan [what to change]`, `/decline [reason]` |
| a gate label has not moved for an hour | `/retry` |

A parked issue (`backlog`) or one that waits for the reporter (`needs-info`) needs no command and gets no comment; `/accept` still works on both. For a plan, the sentence follows the lines the plan worker wrote for plan triage ("Wrong layer", "Work item", "Conflicts with", "Breaking change"), and a work item points at the **Spawn Work Items** workflow.

The comment is always the last one. When anyone comments, it is deleted and posted again at the end; when what is waited for changes (a decision becomes a plan), it is posted again, so that people who follow the issue are told; when only the words change, it is edited in place; when nothing waits any more, or the issue closes, it is deleted. The status issue skips it when it looks for reporter replies, or it would hide every reply under it.

**The commands.** The first line of a comment decides (a command in a quote, a code block or a sentence does nothing), and the rest of that line is a reason:

- `/accept` removes what stops the issue at the first gate (`needs-decision`, `scope-review`, `backlog`, `out-of-scope`, `declined`, `needs-info`), reopens it if it was declined, and gives `issue-triage-handoff`, which starts the plan worker.
- `/decline [reason]` adds `declined`, tells the reporter in plain words with the reason, and closes the issue as not planned.
- `/approve` lifts the hold of a classified plan and hands the issue to implementation with `plan-triage-handoff`. It asks the plan approval resume script whether the issue may be handed on (classified, no dependency, not already handed on) and posts the same approval comment, naming the person who gave the command: removing the label with the signal token would have named the owner of the token.
- `/replan [what to change]` gives `issue-triage-handoff` again for a plan that waits for approval; the plan worker reads the comment as the request for a new plan.
- `/retry` gives the gate label that is on the issue again, as the stalled-issue sweep does.
- `/help` lists them.

A command does what the role can already do by hand, and no more. The role is read from GitHub for the person who commented (`commands-need`, triage by default; a personal repository has no triage role, so write is the floor); the issue acted on is the issue of the event; the text of a comment is never passed to a shell or a model, and a reason is echoed with its mentions made harmless. A collaborator below the role gets one reply saying so, a stranger gets nothing, and a refused command gets a confused face and a reply that says why. A label removal uses the workflow token and starts nothing; the label that hands an issue on, and a close, use `SIGNAL_TOKEN`, because those are what start the next gate. The Concierge still never lifts a hold by itself: a person gives the command, and the comment names the person. An issue that carries `no-auto-processing` refuses every command.

**A command is not a reply.** A comment that starts with a command starts no issue worker run: the condition of `workflows/issue-worker.md` skips it, and a test keeps its list equal to the commands the parser knows. Before, `/accept` started a run of its own, and a run that a reporter's reply had started a minute earlier could finish after the hand-over, so that issue triage found an issue with no gate label (they are removed as an issue moves on, and the plan worker was still writing) and put `needs-decision` back. That second race is closed by a record, not by a guess. When `/accept` runs, the Concierge has already checked the role of the person in code, and it writes a comment of the bot that names them and carries the marker `concierge:accepted`, before the label that hands the issue on. Issue triage reads that record in a deterministic pre-activation step, without a model, and stands down when it finds one; the step takes the label that started the run away and the activation condition reads the step's outcome, as the PR worker's does for an open pull request. The prompt has the same rule as a second layer, for the case that the step could not read the comments. Only a comment of the bot counts, so the same words in a comment of a person are only words, and the role is the one the commands check (`triage` by default), not the author association. The first attempt at this keyed on the association of the maintainer's own `/accept` comment, and the proof of v2.0.0 showed why that cannot work: GitHub shows a member whose membership is private as a CONTRIBUTOR to the token of a workflow, so the model read the maintainer as a stranger (docs/e2e.md). Scenario 10 is the proof; the decision is also a check of its own there.

What the design cannot do, and what covers it: a label removed by hand starts nothing here (only the issue worker and the plan approval resume may start on a removal), so a menu that is left over is removed by the hourly run or by the next event on the issue; and the gates post their comments with the workflow token, which fires no event, so a label event waits half a minute before it looks at the comments, and a menu that still ends up above a gate's comment is moved by the next event or the hourly run. `workflow_run` would close that gap, but it adds a skipped run to the Actions tab for every label event.

Not seen live yet: the commands in Actions, whether the workflow token may read a collaborator's permission, and the ordering after a gate's comment. `scripts/commands.test.mjs` and `tools/commands-workflow.test.mjs` pin the rest, and scenarios 10 and 11 prove the path in the sandbox.

### Pausing the Concierge

A maintainer can stop the Concierge in a repository without touching a workflow: create the repository variable `ISSUE_CONCIERGE_PAUSED` with the value `true` (Settings › Secrets and variables › Actions › Variables). To resume, delete it or set it to anything else. The variable was called `CONCIERGE_PAUSED` in v2.0.x and that name still pauses, so that a pause does not lift when the Concierge is updated: either one set to `true` pauses, and every reader (the conditions, the commands, the status page) reads both. In an organisation repository write access is enough to edit a variable, in a personal repository collaborator access ([decision 0037](decisions/0037-the-concierge-is-paused-by-a-repository-variable.md)).

**Why a variable.** A gate has to be stopped before it starts: a run that starts costs a runner and, for a gate with a model, credits. The only repository-wide value that an `if:` can read is a repository variable. A label on another issue, a file or a comment cannot be read without a job, and a job for every event is what pausing is meant to avoid. A run skipped by its `if:` costs nothing and uses no AIC.

**What stops.** Every gate (issue worker, issue triage, plan worker, plan triage, PR worker, PR triage, release closer) and every plain workflow that acts on an issue or a pull request (janitor, dependency watch, plan approval resume, PR ready signal, related repo closer, reporter notify, waiting for release, stalled issue sweep). Each reads the variable in its own `if:`. The three with a deterministic step before the agent that writes read it there too: the PR worker and issue triage take a void label away, and the release closer swaps labels and posts a comment. `tools/pause.test.mjs` evaluates every real condition with each of the two variables on and off, and the compile smoke reads the term in every compiled gate and in those steps.

**What keeps running.** The status issue (it shows a PAUSED banner, since when, and how to resume), the commands (a command that would hand an issue on is refused with a reply, because no gate would start; `/decline` and `/help` still work), the updater and the deployment check (they touch no issue), and anything started by hand: a run of a workflow with `workflow_dispatch` is an override and works. Runs already in flight finish.

**After resuming.** Nothing is replayed. A label event that came while the Concierge was paused started nothing, so an issue that was in a gate then stays there; the status issue lists it as stuck after an hour, the options comment offers `/retry`, and the stalled-issue sweep heals an issue the issue worker had analysed.

Not seen live yet: the variable in a real repository, and whether the workflow token may read the date it was set (the banner then says "Paused" without a date).

### Settings

`.github/issue-concierge/settings.yml` (template `shared/settings.yml`) belongs to the repository, like `scope.md`: reviewed by pull request, read from the default branch, every setting with a default. A line that cannot be used is reported by `check-deployment` and on the page, and the default stays. `status-issue` is on by default; set to `false`, the issue is closed and unpinned, never deleted. `commands` (on) and `commands-need` (`triage`) switch the commands and the options comment and set the role that may use them. `mention-after-days` (0, never) is the nudge above. The format is flat `key: value` lines, which a short parser reads without a dependency (`scripts/issue-concierge-settings.mjs`).

Not seen live yet: the first run in a sandbox, whether the fine-grained `SIGNAL_TOKEN` may pin, and the pinned issue as the bot creates it. `tools/status-workflow.test.mjs` and the tests beside the scripts pin the rest.

## Opting an item out

An issue or pull request that carries `no-auto-processing` is never touched by the Concierge. The rule is the decision record [an item labelled no-auto-processing is never touched](https://github.com/gearsnlevers/issue-concierge/blob/main/docs/decisions/0028-an-item-labelled-no-auto-processing-is-never-touched.md).

**Why it exists.** The issue worker starts on any new, edited or reopened issue and on any comment, and a maintainer's comment on frodo-cli#518, an issue from before the Concierge that had never been through it, started intake, then triage, then a plan with a hold label, three bot comments in all. The maintainers wanted to handle that issue by hand and had no way to say so. Closed issues and bot-authored issues already start nothing ("Who may start when", "Bot activity is not work"); this is the equivalent for an issue a person wants out.

**What it stops.** Everything: no gate starts, nothing is labelled, commented on, planned, assigned or closed, and a closed issue gets no "Fixed in" and no "Included in" comment. The guarantee is the `if:` of each workflow, so no run starts and nothing is spent; the scripts check the label for the items they pick from a query. A prompt that repeats the rule is only a first layer.

| Workflow or script | Where the label is checked |
|---|---|
| issue worker | `if:` (the issue's labels in the event); the `unlabeled` event starts it only for this label |
| issue triage, plan worker, plan triage | `if:` |
| PR worker | `if:` and the live check of the `existing_fix` step |
| PR triage | `if:`, on the pull request's labels |
| Waiting for Release | `if:`, and the script |
| release closer | the `included_fixes` step skips it, and the prompt repeats it |
| janitor | `if:` for events, `scripts/janitor.mjs` for sweeps and manual runs |
| reporter notices | `if:`, and the script for the issue and for its original |
| plan approval resume, PR ready signal | `if:`, and the script |
| dependency watcher | `if:` for the label event, and the script's loop |
| related-repo closer | `if:`, and the script for the canonical issue and for the original |

**Handing an issue over.** Removing the label starts the issue worker once: it listens for `unlabeled` and its condition lets that event through for this label only (removing any other label starts nothing). It then follows its other conditions: the issue must be open, not written by a bot, and not a pull request. A manual dispatch of the issue worker works on a labelled issue, because a dispatch carries no issue payload and is the explicit act of a person.

**Limits, on purpose.** The label belongs to the item that carries it. A pull request is its own item: a labelled pull request is skipped by PR triage, the janitor and the ready signal, and a labelled issue does not opt out a pull request somebody opened for it. The dependency watcher still reads the state of a labelled issue that another issue depends on, because it cannot tell whether that issue is finished otherwise; it changes nothing on it. The label is applied by a person only: no gate adds it, and none removes it.

## Split-repo routing (linked issues)

When a repository defines `.github/issue-concierge/related-repos.md`:

1. The issue worker decides, from evidence, whether an issue belongs in a related repository (see "Evidence before routing").
2. When it does, it creates a canonical issue there, which starts held (see "A routed issue starts held") and carries `original-in-related-repo` (see "Both issues of a link carry a label"), and cross-links both sides with plain-language comments.
3. It applies the internal label `related-repo` to the original issue and does not emit `issue-worker-ready`.
4. The original issue stays open. Issue triage ignores it for planning.
5. When the canonical issue is closed as completed, `related-repo-closer` (a plain workflow with a script, no model; it starts only for an issue that carries `original-in-related-repo`) updates the original issue: it closes it with a short notice, or labels it `waiting-for-release` and comments when the original's `related-repos.md` says a release of its repository is needed first (see "The closer is code, not a model").
6. When the canonical issue is created, and again each time it needs more information from the reporter, `reporter-notify` mentions the person who reported the original issue (see below).

**Decide from the text.** On frodo-cli#887 (2026-10-23) the worker (model `small`, 7 turns, no file read) added `related-repo` with confidence HIGH and the rationale "per related-repos.md", and opened a canonical issue in the library. The CLI's own `related-repos.md` told it to send authentication flows, and "most issues", to the library; the wrapper messages in the report ("Error getting tokens", "Error authenticating user") are produced by the library; the cause, a terminal read that failed with `EAGAIN`, was in the CLI. The library's plan worker then planned a wrong-layer fix and the coding agent started one (frodo-lib#785). So the `when` text and the notes are a guide to where to look, never proof, and the worker now decides from the report text in this order, without searching. (1) It takes the innermost error (or, without one, the behavior described), not the wrapper another layer put around it. (2) It applies the layering the repository states (the ownership lists in `related-repos.md`, and `AGENTS.md` or its decision records when the file points to them; this outranks the `when` text and any keyword). The default is to keep the issue here, and a keep needs no tool call. (3) It routes only when the report itself names the failing component in the related repository: a stack-trace path or a package of that repository, that repository's own command or API as the call that failed, or an error that only that repository can produce, in the innermost position. A keyword from the `when` text, a wrapper message or the name of a command that exists in both repositories is not enough, and it does not search to decide: a command in this repository that wraps a library function matches in both repositories, so a search finds both and settles nothing. (4) It quotes those words in the `rationale` it gives for `related-repo` and gives `confidence: HIGH` only with the quote. Without them the issue stays here and the comment says which part might belong elsewhere. Budget: the run used 7 of its 10 turns and 1.03 AIC; the routing decision adds no search, so a keep and a route take about the turns they took before, and `max-turns` and `max-ai-credits` do not change. **Keeping is the safe side**: the plan gate reads the code, and when its layer check finds that the fix belongs in the other repository it says so and holds the issue for a maintainer, so an issue that stays here by mistake costs a comment, while one routed by mistake costs a canonical issue and a plan in the wrong repository. The prompt is the first layer; the second layers are the hold on the canonical issue and the plan worker's layer check ("Layer check" under the plan gate).

*How the step got here (three versions, two replays).* The first version made the worker search the code of both repositories for every issue. Before release, a replay of 33 historical issues whose correct repository is known (from where the fixing pull request landed; the small model `claude-haiku-5.5` and the default `claude-sonnet-5.5`; one pass per cell) compared the current rule A with a corrected rule B, each with and without code-search hits handed to the model. Accuracy, small / default model: A 78.8% / 93.9%, B 90.9% / 90.9%, A with hits 72.7% / 93.9%, B with hits 81.8% / 90.9%. On rule A both models still routed frodo-cli#887 and #527 to the library because the `when` text names authentication flows; rule B alone gave 90.9% on both with almost no wrong routes (the small model's confident wrong routes fell from 2 to 0), at the price of keeping about a third of the true library issues in the CLI; and hits on the outer error text or the command did not help and, for the small model, hurt. The second version therefore decided from the text and used two searches only to confirm a route (this repository first, then the related one; route only when the related one holds the failing code and this one nothing). A second replay (variant C: rule B plus that confirm step, with the two search results supplied for each issue) scored 75.8% on the small model and 81.8% on the default one, below rule B alone: it kept every issue that belonged here (keep recall 100%) but routed only 1 of 9 and 3 of 9 true library issues, because a CLI command that wraps a library function matches in both repositories and the "both repositories match" rule then keeps it, and all of the small model's misses said "both searches found matches". So the final version has no search in the decision: the text decides, and the cheap error (an issue that stays here by mistake) is caught by the plan gate. Caveats: one run per cell, 33 scored issues (a few items move the percentages by several points), rule B was written after #887 (the rows without #887 give the same picture), the code-search hits in the replay were file lists over today's default branches and hand-picked cause terms, cruder or luckier than what a live worker finds, and the replay cannot measure tool use or turns.

**A routed issue starts held.** The canonical issue is created with the label `plan-approval-required`, through the `labels` option of the `create-issue` safe output (gh-aw v0.92.0 applies it when it creates the issue, and `tools/ci-compile-smoke.sh` reads it in the compiled lock). The gates still run on it, so a plan with its layer check is there when a maintainer looks, but no coding agent starts until a maintainer removes the label: `plan-approval-resume` then hands the issue on (removed before plan triage ran, it hands nothing on and the issue goes through the gates as usual). The trade-off is one click for every routed issue, against a wrong routing costing a comment and not a pull request. To switch the default off, delete the `plan-approval-required` line from the `labels` list under `create-issue` in `workflows/issue-worker.md` and release (keep `original-in-related-repo`: the closer needs it). A per-deployment switch in `related-repos.md` is not offered: the updater a deployment runs is the previous release's, so a setting it does not know yet would apply one release late.

**Both issues of a link carry a label.** `related-repo` marks the original, the issue the reporter filed. The canonical issue, in the repository that holds the work, had only the `Reported from {owner}/{repo}#{number}` line in its body, which a list of issues does not show, so nothing in a list told a maintainer that frodo-lib#804 had an original in frodo-cli (2026-10-25). `original-in-related-repo` marks the canonical issue. It is applied by the `create-issue` safe output (the `labels` option, next to the hold), so the model never chooses it and `add-labels` does not allow it; it is declared in `requirements.json`, so the updater creates it in every deployment. `related-repo` is unchanged and stays on the original; the new name pairs with it without renaming it, so no accepted record changes. The related-repo closer now starts only for a closed issue that carries the new label (the `if:` of the workflow is the guarantee, and `tools/related-repo-closer-workflow.test.mjs` pins it). Before, every close of an issue not opened by a bot started a model run to look for a `Reported from` line (about 2 AIC on the run for frodo-lib#804, measured 2026-10-25); now no close starts a model. Two trade-offs. A canonical issue opened by hand needs the label, or closing it closes nothing. And while a rollout is in progress, a repository that still runs the previous release opens canonical issues without the label: update the repository whose issue worker routes (the one that opens canonical issues) before the repository whose closer closes the originals, or add the label by hand to an issue opened in between. The canonical issues that existed when the label was introduced were labelled by hand.

**The closer is code, not a model.** On 2026-10-25 the model-based closer ran for frodo-lib#806, the canonical issue of frodo-cli#922, and aimed its comment and its label at frodo-lib#806 itself, the closed issue, instead of frodo-cli#922. The safe-output step then failed with HTTP 403, because the token it used belongs to the other repository, and the original was never updated. The run for frodo-lib#804 earlier that day had named the right issue, so the same prompt got it right once and wrong once. Everything the closer decides is in data it can read (the link line, the original, the original's `related-repos.md`), so it is now a plain workflow with a script, `scripts/related-repo-closer.mjs` (code decides what code can decide, record 0011; records 0026 and 0027). The rules it applies:
- Only a canonical issue counts: it carries `original-in-related-repo`. Who opened it is not asked: GitHub reports an author's association relative to what the reading token can see, and the workflow token does not see a private organization membership, so on the first live run an issue that a maintainer had opened (frodo-lib#806) looked like a stranger's and was skipped. The issue text is not trusted. The `Reported from` line only names a candidate, which must be in this repository's `related-repos.md`, carry `related-repo` and have a comment from the harness that names the canonical issue (the proof `reporter-notify` uses). Exactly one candidate must confirm, and it must still be open.
- Only a close as completed counts. A close as not planned or as a duplicate changes nothing and the run says why: a maintainer decides what the original says. (Before, the original was labelled as waiting for a release, or closed as if the work were done.)
- The original's own `related-repos.md` decides between `waiting-for-release` and closing. When it cannot be read nothing is changed and the run fails, visibly.
- A second run finishes what a first one left: the script looks for the label and for its own marker comment (which names the canonical issue) before it writes.
- Reads use the workflow token and writes use the other repository's token. The updater writes it into the workflow's environment (`CROSS_REPO` and `CROSS_REPO_TOKEN`, from the marker `# concierge:cross-repo-env`), and `check-deployment` verifies it.

The workflow can be run by hand for one issue (`issue_number`, and `dry_run` to report only), which is the way to repeat a close that was missed. It replaces the gh-aw definition `related-repo-closer.md`: a deployment's updater removes the old definition and its lock file and adds the workflow and the script. `scripts/related-repo-closer.test.mjs` runs the decisions against fake GitHub answers and the whole script against a fake `gh` that refuses a write made with the wrong token, as GitHub did on frodo-lib#806; `tools/related-repo-closer-workflow.test.mjs` pins the workflow. Not yet seen live.

**Only say what was checked.** On the same run the worker wrote "No change after this issue was opened touches the authentication code" without a search or a commit listing in the run. The analysis comment may now state only what a tool call in that run showed, and the "already fixed or cannot reproduce" steps are tool calls, not impressions.

**Who is told.** The canonical issue is created by the harness, so its author is not the reporter, and GitHub only notifies people who take part in a thread. Without a mention, the reporter would never see a request for information on the linked issue. GitHub cannot subscribe another user to an issue; being mentioned in a comment is what subscribes a user to the thread. The mention is written by a plain Actions workflow, `reporter-notify` (no LLM), not by the issue worker: gh-aw's output step neutralizes every `@handle` in an agent's comment except the people who take part in the event, so a mention the model wrote for the original reporter would reach nobody. The issue worker's prompt therefore tells the model not to write one.

**The incident behind the link notice.** On 2026-10-24 the worker opened frodo-lib#803 to #806 from frodo-cli#919 to #922. The cross-repository token is a maintainer's personal access token, so the four issues have that maintainer as their author, and the people who reported the originals (cli#919 to #922) were not part of them: nothing the plan, triage or a decision wrote there reached them, and the request notice below only covers the case where more information is needed. One mention when the issue is linked subscribes the reporter to the thread from the start. A bot identity for the token (so that the issues do not appear in a maintainer's name) is a separate, later change.

`reporter-notify` posts two kinds of comment, each at most once, each with its own hidden marker.

- **The link notice** is posted once per linked issue, as soon as the original confirms the link: `Original report: {owner}/{repo}#{number}, reported by @{login}. Updates are posted on both threads.` It needs no label.
- **The request notice** is posted when `needs-info` is applied to an open issue (issue triage applies it when the worker's comment asks for details): one comment per request that starts with `@{login}`, thanks the reporter, and points at the request above.

Both notices use the same proof. The login is the author of the original issue as GitHub returns it, never a name found in text, because issue text is written by whoever opens the issue and a crafted report could otherwise make the bot mention anyone. It acts only when all of these hold, and says why it skipped otherwise:

- The issue body has a `Reported from {owner}/{repo}#{number}` line (at the start of a line; a note may follow the number, as the worker wrote on frodo-lib#806, because the line only names a candidate that the later rules confirm), and that repository is a related repository listed in this repository's `related-repos.md`.
- The original issue can be read (a private or deleted original is skipped silently), is not a pull request, and still carries `related-repo`. Removing that label is how a maintainer unlinks the two issues, and it stops the notifications.
- The original issue has a comment by `github-actions[bot]` that names this issue (`owner/repo#number`, as a whole reference). Anyone can write a `Reported from` line; only the harness writes that comment, so a link to someone else's issue fails here.
- Exactly one linked original passes, and its author is a person (not a bot, an app or the coding agent), not a maintainer of the original repository (`OWNER`, `MEMBER` or `COLLABORATOR` as GitHub reports the author's association; they already follow the work) and not the person who opened this issue (they take part already).
- The author has not commented on this issue yet. The link notice has not been posted before (a comment by the bot with its marker; a person who quotes the marker cannot switch it off), and, for the request notice, this request (the latest comment of this repository's issue worker) has not been mentioned before. A reporter who answers is a participant from then on and gets GitHub's normal notifications.

The comment contains exactly one mention and no internal terms. It does not trigger the issue worker, which ignores comments by bots. If the original repository is private, nothing is posted.

**Why the reporter may be mentioned twice, and why that is harmless.** A reporter who got the link notice is already subscribed, so the first request for information reaches them anyway; the request notice adds a prominent, actionable ask. The two notices have different markers, each is posted at most once per link or per request, a comment written with the workflow token starts no workflow, and a second run finds the markers and skips. The most a thread gets is one link notice plus one notice per request.

**The race, and when the workflow starts.** The proof (`related-repo` on the original and the bot's comment that names the linked issue) is written a moment after the linked issue exists. The issue worker's safe outputs run in order after the agent finishes: they comment on the original with a placeholder, create the linked issue, label the original, and only then rewrite the placeholder to the full reference. In the real run on frodo-cli#887 (2026-10-23) the linked issue was created at 20:45:51.96, `related-repo` was added at 20:45:53.16 and the comment named frodo-lib#783 at 20:45:54.97, about three seconds later. A workflow that starts on `opened` normally needs longer than that to queue and check out, but nothing guarantees it, so the first run may find the proof missing. The workflow starts on an issue that has a `Reported from` line when it is opened and when `plan-approval-required` (added at creation), `issue-worker-ready` (minutes later) or `needs-info` is applied. The link notice waits for the proof for at most four checks, 15 seconds apart, and only while that is the single reason for skipping (every other skip, such as a bot, a maintainer, a private original or an unrelated repository, is final at once). The later label events are the second and third chance. If none of them finds the proof, nothing is posted, which is correct for a link nobody confirmed; a maintainer can run the workflow by hand for the issue. An issue the harness never confirmed (it failed before it rewrote the comment) is never mentioned.

**How the comment names the new issue.** The worker cannot know the canonical issue's number while it writes the comment, because safe outputs run after the agent finishes. It therefore gives the `create-issue` output the fixed temporary id `aw_canonical` and writes `#aw_canonical` in the comment, with no owner or repository in front of it. gh-aw registers the id when it creates the issue and then replaces every `#aw_canonical` with the full reference (`owner/repo#number` for another repository). Two things break this, and `tools/issue-worker-linked-issue.test.mjs` pins both: an id the model invents instead of the one it set (the placeholder stays in the comment, as on frodo-cli#694, which read `rockcarver/frodo-lib#aw_lib694`), and a repository written in front of the token (gh-aw would double the prefix).

## Routing back

A link can be wrong. The plan gate may find that the fix belongs in the repository the issue came from ("Wrong layer"), or a person may read the code and see it. Until the first such case there was no way back: plan triage tells a maintainer to "move or re-route" the issue and nothing did it, removing `related-repo` from the original starts nothing (only the removal of `no-auto-processing` restarts the issue worker, and it would see the link comment and keep the issue routed), and the closer leaves a canonical issue closed as not planned "to a maintainer". On frodo-lib#803 (2026-10-26) the plan wrote "Layer: not verified ... probably in frodo-cli" about code it had not read, while the code that had to change (`getTreeDescendents`) was in the library, so a maintainer had to ask whether it could be flipped back.

`Concierge 4g ▸ Route Back` ([decision 0031](decisions/0031-the-work-of-a-link-is-routed-back-by-one-explicit-act.md); plain Actions, no LLM) moves the work back in one act that a maintainer starts by hand for the canonical issue, with an optional dry run. Nothing starts it by itself ([decision 0005](decisions/0005-a-maintainer-holds-the-levers-of-the-pipeline.md): moving work to another repository is a maintainer's decision). In order:

1. The proof of the link is the closer's (`verifyOriginal`): the `Reported from` line only names a candidate, which must be in the related repository, carry `related-repo`, not be opted out and have a comment from the harness that names the canonical issue.
2. The original gets the hold `plan-approval-required` (when it has none), a plain-language comment that names the canonical issue and links the plan written there, and then loses `related-repo` and gets `issue-triage-handoff`. The plan gate of that repository writes a plan against its own code, with the old plan as a lead, and the hold stays until a maintainer reads that plan. The comment is the only text the reporter sees; it names no label or gate.
3. The canonical issue gets a comment that names the original and is closed as not planned, which the closer leaves alone. It is closed last, so an open canonical issue always means unfinished work.

Each step checks first whether it was done, and the order keeps the proof alive as long as it can: the proof ends when `related-repo` is removed, so the two comments name each other, and a run that finds the original without the label but with its own comment, and the canonical issue's comment that names the original, finishes the rest. A forged resume needs both comments, in the related repository. An original that carries `no-auto-processing` is refused: removing that label hands the issue to the issue worker, which is the maintainer's act.

**What travels with a link.** The two workers used to share nothing but the report. On frodo-cli#919 the routing worker read the CLI's code and concluded "The depth limit sits in the library's tree resolution, with the CLI only formatting output", routed the issue on that, and wrote none of it down: the canonical issue held the report and the `Reported from` line, and the comment on the original said "tracked in ...". The plan worker of the library then started from nothing. Now the worker that routes writes a **Routing note** into the canonical issue's body: the words in the report that name the failing component (its rationale, quoted), what it read or searched with the file, or "nothing but the report", and what it did not check. The issue worker of the receiving repository treats the note as a lead and checks the part it can; the plan worker reads it, and for an issue passed back, the plan the other repository wrote, as leads too, reads the code they name before it relies on one, and writes "Layer: confirmed, see {file}", "Wrong layer: ..." or "Layer: not verified" with no repository named as the likely home of the fix. A lead is never a fact: both repositories are public and the text is read as untrusted, like the report.

## Work in more than one repository

A fix can need a change in two repositories: a library function and the command that calls it. The Concierge used to know two answers about where an issue belongs, keep it or route it (the layer check says "Wrong layer" or nothing), and no way to say "both". Splitting was a person writing the second issue and its `Depends on:` line by hand, as for the facade chain.

**Intake does not split.** The issue worker decides from the report text (record 0009) and is the one gate open to every reporter (record 0007), so it keeps an issue that needs work on both sides, says in its comment which part might belong in the other repository and why, and creates nothing there. A split created from a guess about untrusted text would cost a held issue in another repository; a split proposed from code is cheap to check.

**The plan proposes.** The plan worker reads the code on both sides (the layer check) and, when the fix needs a change in this repository and in the related one, writes one line per repository: `Work item: {owner}/{repo} | {what changes} | where: {file or function} | order: {first, independent or this}`. `this` is the line for the repository that holds the plan; `first` says that its own change needs the other one done first (merged, and released where `related-repos.md` says so); `independent` says neither waits. Plan triage holds such a plan (`plan-approval-required`, no hand-off) like a wrong layer and says that a maintainer splits it, or removes the hold if this repository's part can go on alone.

**A maintainer splits it.** `Concierge 2d ▸ Spawn Work Items` ([decision 0032](decisions/0032-a-fix-that-needs-two-repositories-is-split-from-its-plan-by-a-maintainer.md); plain Actions, no LLM) is run by hand for the issue that holds the plan, with an optional dry run. For each line that names the related repository it:

1. creates the work item there as an issue of its own: the sentence of the plan, where to look, `Part of {origin}` and a link to the plan, held for plan approval. It carries no link label and no `Reported from` line, so the closer and the reporter notice do not start for it, and a `Part of` issue is never routed by the issue worker there and never split again;
2. comments on the origin about it. For `order: first` the comment carries a `Depends on:` line and the origin gets `dependency-required`: the dependency watcher then waits for the work item to be merged, released, installable and pinned (the rules of `shared/dependencies.md`), and starts the origin again, which is planned against the real code and goes through its own PR gate. The hold on the origin stays until a maintainer removes it. An `independent` item is only named.

The origin is the tracker and the last link of the chain, so nothing new is needed to close it: it closes with its own pull request, as before. Each repository's pull request is made by that repository's gates; no agent edits two repositories.

**Trust.** The plan is model output written from an untrusted report, so the script believes only what it can check: the repository must be the related repository this deployment is configured for (and nothing is created when the plan names another), every `Work item:` line must have the exact form, two lines for one repository stop the run, and the text that reaches the new issue is one bounded line without mentions or HTML comments (a marker must come from the script). The new issue starts held and the plan of the origin was read by the person who ran it.

**Each step checks first**, so a run that stopped half way is finished by running it again: a work item that was created is found by the comment on the origin or, failing that, by the marker in its body (through the search API, which lags a minute).

**What it does not do.** It does not perform the release or the pin bump of the first part: the watcher detects them (a Dependabot bump of the pin wakes it) but a maintainer or Dependabot does them. It supports one related repository, because the updater generates one token pair (more repositories need a token per repository, which a maintainer must read in the updater). It does not wait for `independent` items when it closes the origin, and it does not start itself on approval: both are the next steps if they prove worth it.

## Gates

### 1. Issue gate
**Worker** → plain-language analysis comment + internal `issue-worker-ready`  
(or `related-repo` and no ready label if linked elsewhere)  
**Triage** → internal quality/priority labels. Emits `issue-triage-handoff` when actionable; applies `needs-info` otherwise. Skips issues that already have `related-repo`.

#### Scope check

Optional, and off unless the repository has `.github/issue-concierge/scope.md` (template: `shared/scope.md`: Purpose, In scope, Out of scope, Needs a maintainer, Where to go instead). When it exists, the issue worker compares each request with it as written and says one of three things in its analysis: in scope (continue), out of scope (the request matches an item under "Out of scope", or a plain statement that the project does not do it), or unclear (it is not excluded, but it matches "Needs a maintainer" or the worker doubts it fits the Purpose). When it hesitates between out of scope and unclear it chooses unclear, and it never calls a request out of scope because it is large, hard, risky or unusual, only because the file excludes it. A bug in something the project already does is always in scope.

Triage turns that into labels. Out of scope: `out-of-scope`, a short plain-language reply, and the issue is closed as not planned; no hand-off. Unclear: `scope-review` and no hand-off; nothing is closed, and a maintainer decides. These outcomes take precedence over the dependency gate. An issue that already has `out-of-scope` is left alone when the reporter replies, and an issue that already has `issue-triage-handoff` is not re-evaluated. To override a decision, reopen the issue if it is closed, remove `out-of-scope` or `scope-review`, and add `issue-triage-handoff`: the same signal that triage sends for an accepted issue. Because an exclusion closes issues without a human, keep that list short and specific; the wording of each item decides what gets closed.

#### A change to what exists

Not part of the scope check, and not optional. The Concierge picks up fixes and small additions; it does not plan, or hand to a coding agent, a request that changes something that already exists until a maintainer has decided. Scope answers "is this ours?" with a file the repository chooses to have. This answers "may it be changed without a person?" for every repository. The two are separate on purpose ([decision 0034](decisions/0034-a-request-that-changes-what-exists-is-held-for-a-maintainer.md)).

What counts: removing, renaming or replacing a command, an option, an alias, an exported function or a file or data format; changing an interface so that something that works today stops working or reads differently to a script (a signature, the meaning of an option, an output format or an exit code someone may parse, a default that changes what a command does); and changing the architecture (the layers, how the project stores data or authenticates, how it is built or released). Offering a replacement for the thing is such a change, and so is a report that proposes the removal as the fix. A fix, an addition, and a refinement inside what the project documents and tests (a better ordering of results, a clearer message) go through: the aim is that the Concierge keeps picking up bugs and small enhancements. The issue worker judges by the effect and not by the argument ("nobody uses it", "it is safe", "it is urgent"): does a call, a script or a command that works today stop working for someone who changes nothing and upgrades, or give a result they would have to adapt to? When it hesitates between an addition and a change it chooses the change, because a held request costs a maintainer a look and a wrongly passed one costs a pull request that deletes something.

The worker says in its comment what would change and that a maintainer will decide. Issue triage applies `needs-decision`, emits no hand-off, applies neither `backlog` nor `low-hanging-fruit`, and closes nothing: [decision 0017](decisions/0017-the-issue-gate-closes-an-issue-only-on-evidence.md) closes only on evidence, and a maintainer's own deprecation issue is not the bot's to close. The outcome comes before "not urgent" and before "worth doing now", and a reporter's reply does not lift it. To accept, a maintainer removes `needs-decision` and adds `issue-triage-handoff`. The plan that follows is held again when it carries a "Breaking change:" line (see the plan gate), so a removal is approved twice: to be planned, and to be built.

A repository sharpens the check with an optional `.github/issue-concierge/guard.md` (template `shared/guard.md`: Protected, Architecture, Freely changeable). It is read from the default branch like the guidance files and ranks below the safety policy and the rules of the workflow.

Why: on 2026-10-27 two probes in the end-to-end sandbox ([e2e.md](e2e.md)) filed a request to remove `listWidgets` and the `widgets` command, worded as safe, in one case urgent and with a replacement. Both were called in scope. The first was rated "low to medium" risk and parked as `backlog` only because it sounded not urgent. The second was planned in full (about 17 AIC) and held only because plan triage happened to rate the risk high. Nothing in the gates looked at the kind of change; the one brake was a model's risk label. The prompts are a first layer, and the guarantee under them is still the hold that the PR worker's `if:` enforces. `tools/change-guard.test.mjs` pins the wording, and the end-to-end scenarios `removal-urgent-is-held`, `removal-casual-is-held` and `bug-fix-passes` check it live. Not seen live yet.

#### Not urgent, and low-hanging fruit

The worker judges urgency as if every dependency were already finished: waiting for a dependency, a release or another change is never a reason to call an issue not urgent. A valid issue that is not urgent gets `backlog` and stays out of the plan gate, with one exception. When the worker also says the change is small and low in risk (low complexity and low risk, using `complexity.md` and `risk.md` when the repository defines them), triage treats it as low-hanging fruit: it applies `low-hanging-fruit` and emits `issue-triage-handoff`. Only that combination qualifies; a medium change is not low-hanging fruit even when it is low risk. Plan triage still makes the authoritative complexity and risk call afterwards and stops at `plan-approval-required` for high complexity or high risk, so a rough estimate at this gate cannot skip a gate. Why the worker's wording matters: triage reads the latest analysis comment, and an analysis written while a dependency was pending can say "not urgent" because of it. Triage disregards that part once the issue carries `dependency-satisfied`. A maintainer can move a `backlog` issue forward by removing `backlog` and adding `issue-triage-handoff`.

#### Dependency gate

An issue declares a dependency with a `Depends on:`, `Blocked by:`, or `Requires:` line. The issue worker analyzes the issue as usual and still adds `issue-worker-ready`. Issue triage detects the declaration and applies `dependency-required` instead of handing off. `plan-triage` and `pr-worker` also refuse to proceed while the label is present.

The `dependency-watch` workflow (plain Actions, no LLM) resolves dependencies hourly, on demand, when the label is added, and when an issue closes, a pull request merges, a release is published, or `package.json` changes. Satisfied means merged, or closed as completed, in the same repository. For a related repository that requires a consumer release, it also means released, installable from the registry, and pinned by this repository. When every dependency is satisfied the watcher adds `dependency-satisfied`, removes `dependency-required`, and re-applies `issue-worker-ready` with the signal token so issue triage runs again and hands off.

Full rules: `shared/dependencies.md`.

#### A run that ends early, and a second analysis

The worker has 14 turns (`max-turns`), and its prompt asks for at most ten of them for reading and searching, so the comment and the labels always fit; each is a tool call, and a run that reaches its limit first posts nothing. On frodo-lib#803 (2026-10-24) the first run used all ten of its then ten turns on the code behind the report and ended on `429 Maximum LLM invocations exceeded (10 / 10)` with no comment and no label. The `[aw]` failure issue called it a rate limit, which it was not, and the retry that a maintainer's comment started posted its comment and its label and hit the same limit on the closing reply. Measured before: 7 turns and 1.03 AIC on frodo-cli#887 (a report with no code to check), 1.54 AIC on frodo-lib#803, against `max-ai-credits: 16`. When a check is still open at turn ten the worker says what it did not check.

Any event can start the worker again: a comment, an edit, the removal of `no-auto-processing`. An event that adds nothing to an analysis the worker already posted (a comment that only links or thanks, a label change, a typo fix) gets no second analysis: it posts no comment and signals as usual, so triage can run again on the analysis that is there. It writes a new comment only for something a reporter would want an answer to, and then says only what is new. Before this rule frodo-lib#802 got "Thanks for the follow-up" under its first analysis from a maintainer's note. The rule is in the prompt, so it lowers the number of repeated analyses; a model still decides each time.

#### A hold set before triage

A maintainer can add `plan-approval-required` by hand before an issue is analysed, to read the plan before anything is built; the end-to-end sandbox does it to every issue so that no code is written. The hold stops the issue after the plan, not before triage. On 2026-10-27 one of the six cycles of the sandbox's first baseline ([e2e.md](e2e.md)) had issue triage end in a `noop`: the issue "no longer carries `issue-worker-ready` ... and it already has `plan-approval-required`, which means it has moved past triage". The janitor takes `issue-worker-ready` away within seconds on a held issue (see "Stalled issues"), so the trigger label is often gone by the time triage reads the issue, and the model took the two together for a sign that the work was done. Nothing was commented and nothing healed the issue within 35 minutes, because the sweep waits at least half an hour. The prompt now has a section "A hold that is already there", the counterpart of the one in plan triage: the hold is no evidence of being past triage, a missing trigger label is normal, and only the later-phase labels count. A prompt is a first layer; the sweep is the backstop. `tools/issue-triage-hold.test.mjs` pins the wording and the janitor behaviour it describes.

### 2. Plan gate
**Worker** → rough plan + `plan-worker-ready`. For a report that contains an error message or a stack trace the plan says how the likely cause was checked (the file and line it read, or "not verified") and labels an unchecked cause "Hypothesis (unverified)", so whoever approves the plan can see what is established and what is a guess.  
**Triage** → complexity and risk labels.  
If complexity is high or risk is high, add `plan-approval-required` and do not emit `plan-triage-handoff`; the comment says which ("High complexity.", "High risk." or "High complexity and high risk.") and how to resume. Otherwise, unless the issue already carries `plan-approval-required`, emit `plan-triage-handoff`. When the hold is already there (a maintainer added it by hand), plan triage classifies, emits no hand-off, adds no second label and posts no comment.  
**Layer check.** In a repository with `related-repos.md`, the plan worker notices which repository holds the code that has to change when it reads the code for the cause: it takes the innermost error, not the wrapper another layer put around it, and searches the related repository when the report could belong there. If the fix belongs in the other repository, or an issue routed here belongs where it came from, the plan starts with "Wrong layer: the fix belongs in {owner}/{repo}, see {file}". Plan triage treats that line like a conflict with a decision record: it classifies, adds `plan-approval-required`, emits no hand-off and says that a maintainer has to move or re-route the issue. Without it, a wrong-layer plan on an issue that is low in risk went straight to a coding agent in the wrong repository (frodo-lib#785). When the worker read nothing that settles the layer it writes "Layer: not verified" and does not guess. Cost: one more search in the related repository, about 1 AIC, so the worst case of about 19.5 AIC becomes about 20.5 against a `max-ai-credits` of 24.  
**Breaking change.** The issue gate holds a request that changes what exists before any plan (see "A change to what exists"), but a request that reads like a fix can turn out, once the code is read, to need a removal, a rename or a change of behavior. The plan worker then writes a line that starts with "Breaking change:", naming what changes and the file it read, and plan triage treats it like "Wrong layer": it classifies (and lowers neither label because the plan calls the change small), adds `plan-approval-required`, emits no hand-off and says that a maintainer has to decide. This is the second layer; the first is the issue gate.  
Plan triage never resumes a held issue itself. Removing `plan-approval-required` is the signal; `plan-approval-resume` applies the handoff. The prompt is the first layer; the PR worker's `if:` and its `existing_fix` step are the guarantee, because a model can ignore a sentence and the label allow-list cannot depend on the issue's state.

**Planned once.** Any comment can end in a plan: the issue worker signals after a reply that adds nothing (see "A run that ends early, and a second analysis"), issue triage hands the issue on again, and the plan worker used to write a second plan. On 2026-10-27 the first baseline of the end-to-end sandbox ([e2e.md](e2e.md)) had the reporter answer a plan with "Thanks, this is what I meant." and got a second plan of about 15 AIC in three runs out of three. The plan worker now looks for a plan of its own first (the author and the marker of "Plan comment identity"), before it reads any code. A plan that still covers the issue stays the only one. A new plan is written when the issue was edited with new facts, when someone answered a question the plan or the analysis raised, or when someone asked for a new or a different plan in a comment, which is also how a maintainer asks for one. When the plan stands nothing is posted, and `plan-worker-ready` is given again only when the issue has no `complexity/*` and `risk/*` label, that is when plan triage never classified the plan: a lost hand-off still heals and a classified plan is not classified twice. A prompt is a first layer: the run still starts and reads the comments. A guard that skips the run before it starts was left out on purpose, because it would also stop the one run that can still give plan triage its hand-off. `tools/plan-worker-already-planned.test.mjs` pins the wording.

Why risk counts, not only complexity: a change can be small and still sit in a place where a wrong fix is costly (authentication, data integrity, public API). Without the stop, such an issue went straight to the coding agent on a plan that was still a hypothesis (frodo-lib#783: complexity low, risk high, handed to the coding agent three minutes after triage, with a cause that turned out to be in the wrong layer). The stop is the human lever between "this is what we think is wrong" and code. The PR gate is unchanged: human review is still required unless both complexity and risk are low.

Two consequences. An issue that is planned again (see "Planned once") gets the stop again and needs a new approval, as it always did for high complexity. And an issue that already passed the plan gate keeps its place: the rule applies when plan triage runs, not retroactively.

### 3. PR gate
**Worker** → assigns coding agent (triggered by `plan-triage-handoff`)  
The PR worker never reads the issue: its activation condition (an `if:` on the label event) already excludes bot-authored issues and issues labeled `dependency-required`, and the instructions it passes to the coding agent are static: configured as `custom-instructions` on the safe output and sent with the assignment as `agent_assignment.custom_instructions`, not written by the model (an instruction that only travelled in the model's `rationale` never reached Copilot, which is why frodo-lib#764 did not get its `pr-worker-ready` label). Reading untrusted issue content is blocked by gh-aw's integrity policy unless a workflow opts out with `min-integrity: none`, which made the worker refuse to assign the agent (frodo-lib#760); this design needs no such opt-out.

The assignment is sent without issue-intent metadata (`issue-intent: false`). With it, gh-aw sends the agent's `confidence` and `rationale` along with the assignee, and GitHub's Agent suggestions preview holds anything below `HIGH` as a pending suggestion that a person must accept on the issue page (frodo-lib#760, confidence `MEDIUM`: the call reported success and nothing was assigned until someone clicked Accept). The gate here is the `plan-triage-handoff` label, which a person or plan triage already decided on, so the assignment is a mechanical step and must not depend on how the model rates its own confidence.

**Ready signal** → the PR gate's triage starts when the pull request carries `pr-worker-ready`. The coding agent is told to add that label but cannot: its GitHub tools do not write labels (observed on frodo-cli#870 and frodo-lib#764: the instructions arrived, the label did not). The `pr-ready-signal` workflow (plain Actions, no LLM) adds it, with `SIGNAL_TOKEN` (Issues and Pull requests: Read and write) so the label event starts triage.

It learns that the agent has finished from the pull request's timeline, where each agent session is recorded as `copilot_work_started` and `copilot_work_finished`. A **sweep every 15 minutes** looks at every open pull request the coding agent opened and signals when the latest session has finished (the newest finish is later than the newest start) and no `pr-worker-ready` label has been applied since that finish. So a finish is signalled once, a feedback round that finishes again is signalled again, a label the janitor removed is not re-added for a finish that was already handled, and a signal that arrived early (someone labelled while the agent was still working) does not hide the real finish.

Why a sweep and not an event (measured on frodo-lib#771): the agent's own `review_requested` starts a run that waits for a maintainer's approval like any run the agent causes (the repository's "Require approval for workflow runs" policy), and `workflow_run` is never delivered for the agent's `dynamic` runs. Two more triggers remain: `ready_for_review` (a maintainer took the draft out of draft) and `workflow_dispatch` (with a pull request number for that one, or without one for a sweep; `dry_run` reports only). Only open pull requests opened by the coding agent are touched.

PR triage runs as a `pull_request_target` run, so it does not wait for "Approve and run workflows". As a `pull_request` run it did: GitHub holds every run on a pull request the coding agent opened. gh-aw accepts `names:` only under `pull_request`, so triage listened for every `labeled` event and filtered by name inside the job, which meant each label event on the pull request, including triage's own three labels, queued another held run, and a held run stays on the head it was queued for after the agent pushes again (seen on frodo-lib#771 and frodo-cli#871).

This removes a human step, so the trade-off is stated here. The CI runs on the agent's pushes still wait for "Approve and run workflows", and branch protection still needs those checks, so that click remains the human gate before anything merges. What protects the unattended triage run:

- It runs the workflow from the default branch, and gh-aw refuses `pull_request_target` unless the checkout is off. `checkout: false` means no pull request code is checked out or run; the agent reads the diff through the API.
- The `if:` starts it only for the `pr-worker-ready` label and only for a pull request from this repository. The same-repository guard is one gh-aw adds for `pull_request` and not for `pull_request_target`, so it is written out.
- The label must be added by someone with write access, as for every gate.
- It can write only the fixed list of complexity, risk and handoff labels and one comment, and threat detection stays on.

Its concurrency group includes the label name. gh-aw's default for pull-request triggers is one group per pull request with `cancel-in-progress`. Now that these runs are no longer held, triage's own three labels each start a run (skipped by the `if:`) that enters the group and cancels the triage still finishing. Seen on frodo-lib#775: the `safe_outputs` job was cancelled seconds after the labels and the comment had landed, so any output still waiting would have been lost. With the label name in the key, only another `pr-worker-ready` event for the same pull request cancels a running triage.

What it gives up: nobody looks at the pull request before a model reads it, and the labels it writes feed the merge rules. Do not let auto-merge act on `pr-triage-handoff` without required CI checks, as `deployment.md` already says. To get the approval click back, revert this change (`on: pull_request` with `names: [pr-worker-ready]`) and accept the held runs; the updater rewrites deployed files from each release, so a local edit in one deployment would not last.

**Triage** → re-evaluates against the diff, reports the state of the checks (failing, running, passing, or "CI state not checked" when it cannot read them) and emits `pr-triage-handoff`. It classifies size and risk, so a red check does not hold the handoff back; it changes the recommended next action.

### Environment agent
Optional. Any worker may invoke it if the consuming repository defines it.

### Merge
Branch protection acts on the final labels, and a maintainer merges. Auto-merge is aspirational and enabled nowhere yet: the Concierge never enables it.
